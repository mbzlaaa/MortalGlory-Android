## 3. 本轮工作过程（假设链，全部由原始字节驱动）

### 3.1 假设 A：".resource 的 StreamData 沿用了 PC 旧偏移，指向缩水后的文件 → 越界"
- 手段：自研解析器按 `[2B 对齐填充][u64 offset][u32 size]` 布局，完整解码两文件共
  **446 个 StreamData**。
- 结果：**证伪**。CI 重建时把 `.resource` 的 offset/size 台账**完全重写对齐**：
  - PC：`MAX(offset+size)=109,810,880`，`SUM(size)=109,810,880`，越界 **0** 条；
  - CI：`MAX(offset+size)=18,840,000`，`SUM(size)=18,840,000`，越界 **0** 条。
  - 且 `MAX(offset+size)` 精确等于各自 `.resource` 的实际大小。
- 结论：`.resource` 引用链**完全自洽**，此方向作废。

### 3.2 假设 B："对象表越界" → 证伪
两文件对象表（每条 `int64 pathID + u32 byteStart + u32 byteSize + int32 typeID = 20B`）
的 `MAX(byteStart+byteSize)` 均精确等于 `文件大小 − dataOffset`，**越界对象 0 / 0**。

### 3.3 观测：APK 里根本没有合并文件，只有 1 MiB 分片
- `assets/bin/Data/` 共 **570 条目**；三组 split：
  `sharedassets0.assets` **261 片**（总 272,631,912 B，每片正好 1,048,576 B，
  末片 2,152 B）、`sharedassets1.assets` 8 片、`sharedassets2.assets` 77 片。
- 另有 116 个 **32 位十六进制命名的文件**（16.8 MB）与一个哈希命名的 `.resource`。
- `globalgamemanagers` 的引用清单里，**PC 有 `resources.assets`，CI 没有**（被合并删除）。

### 3.4 假设 C："分片按字典序拼接 → 内容错乱"
- 手段：数值序 vs 字典序拼接后逐字节比较（`split0,split1,split2…` vs `split0,split1,split10…`）。
- 结果：**证伪**。而且发现一个关键事实：**Unity serialized file 是大端序**——
  按大端解码 `split0` 头部得
  `metadataSize=72,589 / fileSize=272,631,912 / version=19 / dataOffset=72,624`，
  **与实际分片总和、与既有解析结果完全一致**，并能在偏移 20 起看到 ASCII `2019.1.8f1`。
  分片首尾相接逐字节连续（split1 尾部 == split2 头部）。
- 结论：**合并内容是正确的**，分片拼接本身无罪。

### 3.5 假设 D："data 文件被 DEFLATE 压缩 → 引擎无法读"
- 手段：检查全部 Data 条目的 zip 压缩方式。
- 结果：APK 里 **568/570 是 DEFLATED，只有 2 个 STORED**
  （`sharedassets0.resource` 与那个哈希 `.resource`）。
- **决定性实验**：用 `zipfile` 把所有 Data 改写为 **STORED** 并把三组分片合并回单文件
  → 426 MB 新 APK → `zipalign -f -p 4` → `keytool` 生成调试密钥 → `apksigner` 签名
  （v1/v2/v3 全通过）→ 卸载旧包 → `pm install` 成功 → 干净抓日志。
- 结果：**仍然 corrupted（1,044 处），一字未变** → 压缩假设**再次证伪**
  （与 A 路线历史结论一致）。

### 3.6 本轮最有价值的新观测（未解释，是后续突破口）
干净 logcat（2717 行）统计：

| 文件 | 是否报错 | 大小 | 类型 |
|---|---|---|---|
| `sharedassets0.assets` | **报错 226+ 次** | 272,631,912 B | SerializedFile |
| `level0` | **报错 296 次** | 641,416 B | SerializedFile |
| `globalgamemanagers` | **不报错** | 54,400 B | SerializedFile |
| `sharedassets0.resource` | **不报错** | 18,840,000 B | 非序列化（原始资源流） |

- 报错原文（指向 APK 内真实路径）：
  `The file '.../base.apk/assets/bin/Data/sharedassets0.assets' is corrupted!
   Remove it and launch unity again!` + `[Position out of bounds!]`
  + `(Filename: ./Runtime/Serialize/SerializationCaching/CachedReader.cpp Line: 220)`。
- 三条候选规律（互相竞争，未判定）：
  1. **只失败于"较大的 SerializedFile"**（≥ ~64 KB 的 level0/sa0 失败，54 KB 的 ggm 通过）；
  2. **只失败于"走 CachedReader 流式读取"的文件**；
  3. `.resource` 不走 SerializedFile 路径，所以永远没事。
- 其它日志信息（用于排除环境）：`SystemInfo CPU = ARMv7 VFPv3 NEON, Cores = 8,
  Memory = 7561mb`、`Version '2019.1.8f1 (7938dd008a75)'`、
  `Scripting Backend 'mono', CPU 'armeabi-v7a', Stripping 'Disabled'`。

## 4. 关键硬事实清单（可复现）

- Unity **serialized file 头是大端序**：`[u32 metaSize][u32 fileSize][u32 version][u32 dataOffset]` + 版本串。
  - `sharedassets0.assets`（CI）：`meta=72,589 / fileSize=272,631,912 / ver=19 / doff=72,624`
  - `level0`：`meta=81,555 / fileSize=641,416 / ver=19 / doff=81,584`
  - `globalgamemanagers`：`meta=7,256 / fileSize=54,400 / ver=19 / doff=7,280`
  - **三个文件的 `fileSize` 都精确等于各自实际字节数** → 头部本身没错。
- 类型/对象表布局：类型表**非定长**（内建类 23 B/条，MonoBehaviour 脚本类 39 B/条，
  多 16 B scriptTypeHash）；`sharedassets0.assets` 类型数 251、对象数约 3,125。
- StreamData 引用点布局：`[2B 对齐填充][u64 offset][u32 size]`，紧随 `.resource` 路径串之后。
- APK 与 PC 数据的构成差异（结构性畸变的来源）：
  | 指标 | PC 原版 | CI 重建 |
  |---|---|---|
  | `sharedassets0.assets` | 43.8 MB | **272.6 MB（数据全内联）** |
  | `sharedassets0.resS` | 251,760,728 B | **不存在（引用 0）** |
  | `resources.assets` | 9,213,024 B | **缺失** |
  | 分片 | 无 | sa0=261 / sa1=8 / sa2=77（各 1 MiB） |
  | Data 压缩 | 未统计 | 568 DEFLATE / 2 STORED |
- 非标准特征（可疑）：一个 Unity 2019 安卓包通常把 Data 文件**未压缩存放并做页对齐**；
  本产物却"**几乎全 DEFLATE + 全部切成 1 MiB 分片 + 116 个 32 位十六进制命名文件**"，
  这看起来**不像 Unity 官方 Android 构建的原始产物**，更像经过某道重打包/重压缩流程。

## 5. 已证伪假设汇总（更新版）

| 假设 | 结论 | 本轮证据 |
|---|---|---|

| DEFLATE 压缩导致读取失败 | **证伪** | 全 STORED 重打包 + 重签名后报错不变 |

| `Library` 旧缓存污染 | **证伪** | B 路线（冷缓存重建）产物缺陷不变 |

| `resources.assets` 缺失是缺陷 | 证伪 | CI 构建自身自洽，引用计数 0 |

## 6. 经验教训（方法论，最重要）

1. **大端序陷阱**：Unity serialized file 是**大端**。用小端解析会得到一堆天文数字并
   让人误判"文件损坏"。**先验大端**，并用 `header.fileSize == 实际字节数` 做自检。
2. **"文件自洽"必须自证**：任何"文件损坏"结论都要用
   `fileSize == 实际大小`、`SUM(size) == 文件大小`、`MAX(offset+size) <= 文件大小`
   这类**恒等式**去闭合，而不是靠"看着像乱码"。
3. **基准（baseline）缺失是最大的方法论漏洞**：我们一直拿 **PC 构建**当参照，
   从来没有一个**已知能跑的同版本 Android 构建**当对照。→ 后续应优先补上这个基准
   （自建最小空场景 Android 工程即可），做**逐字节 diff**。
4. **一次只变一个量**：分片 / 压缩 / 签名 / 对齐逐一隔离，避免"改一堆再试"。
5. **打包层与内容层要分开怀疑**：本轮把打包层（压缩/分片/对齐/签名/缓存）整条排完，
   这是**净收益**——哪怕没找到根因，搜索空间也缩小了一大块。
6. **手机端取证规范**：
   - 禁用 `logcat -d | grep 'Unity'`（会被 AI 自身日志污染）；
   - 用 `logcat -c` → `am force-stop` → `monkey` 启动 → 固定 `sleep` → 按 PID 过滤；
   - 让脚本只输出**短数字/短词**（窗口号、字节数），因为手机截图 OCR 长文本会糊，
     数字比单词更可靠。
7. **终端/环境坑**：
   - 严禁 `set -e` / `set -o errexit`（终端会卡死）；长命令一律 `|| true` 兜底；
   - heredoc 会吞缩进导致 `IndentationError` → **一律用文件写入脚本**；
   - 诊断脚本统一落 `/root/e_diag/`，设备日志落 `/data/local/tmp/`；
   - `sh -e` 下任一子命令非 0 会中断整串命令。
8. **本轮新增的可用能力（重要资产）**：手机端 Ubuntu 里其实**已具备完整签名工具链**
   —— `apksigner` / `zipalign` / `keytool` / `java` 全部可用。
   也就是说"改包 → 对齐 → 重签 → 装机 → 抓日志"这条**端到端本地闭环已经打通**，
   不必依赖云端 CI 就能快速验证修补想法（本轮 7 秒重打包 + 签名就完成了）。
   - 已知约束：`pm install` **读不了 `/sdcard`**，需先 `cp` 到 `/data/local/tmp/`。

## 7. 下一步建议（按性价比排序）

1. **补基准（最高优先）**：用 2019.1.8f1 建一个**最小空场景 Android 工程**并构建，
   得到"已知可运行"的 `assets/bin/Data`。把它与本产物做**逐字段/逐字节 diff**
   ——重点看：Data 文件的压缩方式与页对齐、是否有 1 MiB 分片、是否存在 32 位十六进制
   命名文件、`globalgamemanagers` 的引用清单、SerializedFile 的类型表/类型树开关。
   **这一步直接回答"我们的产物哪里不像一个正常的 Unity 安卓包"。**
2. **验证"分片/重打包来源"**：查清 CI 里是谁把 Data 切成 1 MiB 并全量 DEFLATE。
   （工程配置 `APKExpansionFiles=0`、`androidSplitApplicationBinary=0`，仓库里也没有启用
   分片的配置，所以**来源不明**——这本身就很可疑。）
3. **尝试页对齐**：把 Data 文件按 4 KiB 页对齐后再打包（Unity 常用于 mmap）。
4. 若 1~3 仍不解决 → 转 **F（空壳 + 数据外科手术）** 或 **G（AssetBundle 重封装）**。
5. **安全收尾**：仓库远端 `origin.url` 里**明文内嵌了 PAT**，务必尽快**吊销**
   （本文档不记录任何密钥）。
